# Заявки, согласование и кеш

Срез: 2026-10-03, `547b503580ddde131e47ba655ce3087d9fb0fa5f`. Назад к [общей карте](../PROJECT_MAP.md).

- [App.tsx](../../src/App.tsx) при `meta.documents_enabled` направляет `/transfers/*` в `waybill`, `/writeoffs/*` в `writeoff`. Деталь заявки: `/:resource/documents/:documentId`; аналитика iiko доступна как `?view=analytics`.
- [DocumentsPage.tsx](../../src/DocumentsPage.tsx) управляет вкладками, фильтрами, пагинацией, созданием и карточкой. Вызывает `GET /documents/:kind/options`, `GET /documents/:kind?...&page=`, `GET /documents/:kind/export`, `GET /documents/:kind/:id`.
- Начальный список — статус `Created`; для `waybill` направление `incoming`. `DocumentListItem` в [DocumentListItem.tsx](../../src/DocumentListItem.tsx) предварительно загружает карточку при приближении строки к видимой области (IntersectionObserver, 300px), по наведению, фокусу и касанию. Очередь кеша ограничена двумя параллельными запросами.
- В карточке кнопки берутся из серверного `doc.actions`. `confirm`, `deny`, `cancel` отправляют `POST /documents/:kind/:id/:action` с `version` и `request_id`. После действия список и карточка инвалидируются; если строка больше не подходит `Created`, она удаляется сразу. Состояния `queued` и `sending` опрашиваются каждые 5 секунд.
- Для `waybill` получатель с серверным действием `receive` вводит фактическое количество каждой исходной позиции в карточке. `POST /documents/waybill/:id/receive` передаёт `version`, `request_id` и полный список `{product_id, amount}`; форма проверяет диапазон, ненулевой итог и наличие расхождения. `receipt_state=pending_sender` виден в списке и карточке до решения отправителя. Серверные `confirm_receipt` / `reject_receipt` отправляются с `version` и `request_id`; до подтверждения отправки в iiko нет. Обычное `confirm` сохраняет согласование исходного количества. Карточка показывает исходное, фактическое и разницу; для отклонённого расхождения получатель может повторить приёмку.
- [DocumentEditor.tsx](../../src/DocumentEditor.tsx) создаёт/редактирует/копирует через `POST /documents/:kind` или `POST /documents/:kind/:id/:mode`; товар ищет через `GET /documents/:kind/products`. При неопределённой отправке сохраняет подготовленный запрос для повтора с тем же `request_id`.
- [documentModel.ts](../../src/documentModel.ts) содержит типы, подписи статусов, `documentPayload()` и проверку `receiptPayload()`. Статус `sent` означает принятие iiko, а не подтверждённое проведение.
- Стоимость показывается **только после создания заявки**. Сервер сохраняет `cost_estimate` при создании; список получает сохранённый снимок, карточка может получить обновлённую серверную оценку. Строка списания подписана на предварительно загруженную карточку через `useDocumentSnapshot()` без отдельного запроса на каждый рендер: свежая оценка карточки заменяет снимок списка только при совпадении ID, kind, version, статуса, submission_state и receipt_state; более старый `estimated_at` не заменяет новый. Инвалидация, ошибка или истечение TTL исключают оценку карточки из выбора. [WriteoffCosts.tsx](../../src/WriteoffCosts.tsx) и [writeoffCostModel.ts](../../src/writeoffCostModel.ts) показывают полный итог как «Сумма», неполный — как «Рассчитано: X ₽» с числом позиций без расчёта; отсутствующая оценка или отсутствие рассчитанных позиций — «Нет данных», а подтверждённая цена с нулевой суммой сохраняет ноль. В форме создания нет расчёта, дополнительного запроса или полей стоимости. Проверки: [writeoffCosts.test.mjs](../../tests/writeoffCosts.test.mjs).
- [DocumentPanel.tsx](../../src/DocumentPanel.tsx) — боковая панель от `64em`, полноэкранная модалка ниже; здесь фокус, Escape и запрет закрытия при отправке.
- [DocumentData.tsx](../../src/DocumentData.tsx) создаёт отдельный кеш на `meta.user.id`. [documentCache.ts](../../src/documentCache.ts) хранит данные по API-пути, объединяет одновременные запросы, ограничивает prefetch двумя, защищает от старого ответа через revision. `401/403/404` удаляют приватный снимок; logout уничтожает кеш.
- [DocumentAccess.tsx](../../src/DocumentAccess.tsx) — права рабочих профилей `view/create/approve` по складам и привязка к аккаунту dashboard: `GET /documents/admin/staff`, `POST /documents/admin/staff/:id` с `revision`. Вкладка подключена в [ManagementPage.tsx](../../src/ManagementPage.tsx) при `documentsEnabled`.
- Проверки: [documents.test.mjs](../../tests/documents.test.mjs) — полезная нагрузка/статусы; [documentCache.test.mjs](../../tests/documentCache.test.mjs) — предварительная загрузка, гонки, потеря доступа, удаление из списка.

## Приходные накладные и реализация

- `CommercialInvoices.tsx` подключён на прежних `/invoices` и `/outgoing` (реализация); вкладка «Документы iiko» с `?view=analytics` оставляет существующие таблицы и `/invoices/:id`, `/outgoing/:id` доступными. Вкладка «Наши накладные» использует отдельные складские права, возвращённые сервером, и не назначает доступ к аналитике.
- `GET /commercial-invoices/{purchase|sale}/options` возвращает разрешённые склады, `can_create`, `can_submit`, налоговые ставки и продавца. Списки: `GET /{kind}?limit=25&offset=…`; карточка `GET /{kind}/{id}`. Поиск товаров/контрагентов: `GET /{kind}/products?q=…`, `/counterparties?q=…`.
- Создание: `POST /{kind}`; правка: `POST /{kind}/{id}/edit`; явная отправка: `POST /{kind}/{id}/submit`. Форма передаёт количество, ручную цену, НДС и признак включения НДС в цену. Итоги отображаются только из сохранённого ответа сервера. `commercialInvoiceModel.ts` проверяет ввод и фиксирует `request_id` и `version`; при неизвестном результате повторяет неизменный запрос, блокируя редактор до ответа. Серверные `can_edit/can_submit/can_pdf` определяют действия.
- Для сохранённой реализации `GET /commercial-invoices/sale/{id}/pdf`: `apiPdf()` в `api.ts` использует общую cookie-сессию и проверяет PDF Content-Type. PDF не генерируется из локального несохранённого редактора.
- Панель использует доступный `DocumentPanel` и мобильную полноэкранную модалку; стили `commercialInvoice.css`. Проверки ввода, точности, налогового режима, подготовленного запроса и статусов: `tests/commercialInvoice.test.mjs`.
- `CommercialInvoiceAccess.tsx` во вкладке управления «Приход и реализация» назначает **отдельные** `purchase/sale` права `view/create/edit/submit` на склад через `GET /commercial-invoices/admin/grants`, `POST /commercial-invoices/admin/grants/{native_user_id}`. Полная замена назначений передаёт `version` из `user.revision` и `request_id`. Неопределённый повтор сохраняет снимок запроса; `409` блокирует форму до обновления. UI проверяет наличие соответствующего раздела аккаунта (`invoices`/`outgoing`), показывая предупреждение; рабочие права не включают раздел или вход автоматически и не изменяют права на перемещения/списания.
- На вкладке «Наши накладные» общие фильтры заведений/периода скрыты: список определяется складскими правами. Аналитика iiko сохраняет общие фильтры. «Обновить», закрытие карточки и переход в конечный статус обновляют список. Контрагент в поиске подписан названием и ИНН; для прихода обязателен номер поставщика. История карточки отображает серверные `action`, `actor_name`, `created_at`.

В старой карточке `/outgoing/:id` кнопка PDF появляется только при серверном `header.can_invoice_pdf`. Загрузка `GET /commercial-invoices/existing-outgoing/{id}/pdf` повторно проверяет права и данные исходной накладной.

## Создание контрагентов в iiko

Дополнение 07.10.2026: реализовано в локальной release-копии; production-деплой не подтверждён.

- [CommercialCounterpartyCreate.tsx](../../src/CommercialCounterpartyCreate.tsx) открывается из редактора накладной только при `options.can_create_counterparty`. Форма поддерживает организацию, ИП и физическое лицо; [commercialCounterpartyModel.ts](../../src/commercialCounterpartyModel.ts) описывает типы, проверяет длину ИНН/КПП, очищает КПП вне организации и формирует неизменный запрос с `request_id`. ИНН физического лица необязателен.
- `POST /commercial-invoices/{purchase|sale}/counterparties` возвращает `operation`; проверка — `GET /commercial-invoices/{kind}/counterparty-operations/{uuid}`. ID операции равен `request_id`; состояния `queued`, `connecting`, `sending`, `unknown` остаются незавершёнными, `confirmed` позволяет выбрать созданного контрагента в накладной, `rejected` показывает отказ. `ApiError.detail` сохраняет `409` с `code=counterparty_duplicate` и `candidates` для выбора существующего контрагента.
- Неопределённый ответ повторяется с тем же подготовленным запросом. Незавершённая операция опрашивается и допускает ручную проверку. `options.counterparty_operations` восстанавливает операции после загрузки страницы; `CommercialInvoices.tsx` сохраняет полученные обновления на уровне страницы, объединяя их по ID, поэтому закрытие дочерней формы или редактора накладной не теряет операцию. Пока дочерняя форма открыта, родительская панель не закрывается по Escape; при отправке/неопределённом ответе закрытие дочерней формы блокируется.
- [CounterpartyPermission.tsx](../../src/CounterpartyPermission.tsx) внутри `CommercialInvoiceAccess.tsx` назначает отдельное право создания в общем справочнике: `GET /commercial-invoices/admin/counterparty-grants`, `POST /commercial-invoices/admin/counterparty-grants/{native_user_id}` с `request_id`, `version`, `can_create`. Складские права накладных этим назначением не заменяются. Сервер повторно проверяет разрешение при записи; кнопка в UI не является источником авторизации.
- Проверки модели: [commercialCounterparty.test.mjs](../../tests/commercialCounterparty.test.mjs); типы options находятся в [commercialInvoiceModel.ts](../../src/commercialInvoiceModel.ts).
